SSH connection issue and resolution
Issue 1: SSH key was missing
- Initially, my WSL machine didn't have an SSH key.
- I used gcloud compute ssh, which automatically generated a public and private SSH key pair and registered the public key with Google Cloud.
Issue 2: SSH connection timed out

- Even after generating the keys, I couldn't connect to the VM because the custom VPC didn't have a firewall rule allowing SSH traffic on port 22.

Issue 3: IAP connection failed

- I tried connecting through IAP, but it also failed because the firewall wasn't allowing IAP traffic.

How I solved it:
1. Enabled the required Network Management API and IAP API for troubleshooting.
2. Created a firewall rule named allow-iap-ssh.
3. Allowed TCP port 22 from Google's IAP IP range 35.235.240.0/20.
4. Added the allow-iap-ssh network tag to my VM.
5. Retried the SSH command with --tunnel-through-iap.

>>port 22 is the default port used by SSH (Secure Shell).

>>>A firewall is a security system that controls incoming and outgoing network traffic based on rules.

Think of it like a security guard at a building entrance.
- It allows authorised people to enter.
- It blocks unauthorised people.
- It follows predefined rules.

what did atlantis.yaml file have
Bro, this is the exact atlantis.yaml file we created in your repository root:

version: 3

projects:
  - name: gcp-infrastructure
    dir: variables
    workspace: default
    autoplan:
      enabled: true
      when_modified:
        - "*.tf"
        - "../modules/**/*.tf"

What does each field mean?
Field

Meaning

version: 3

Atlantis configuration file version.

projects:

Defines Terraform projects managed by Atlantis.

name

Project name: gcp-infrastructure.

dir: variables

Terraform root module is inside the variables directory.

workspace: default

Uses Terraform's default workspace.

autoplan: enabled: true

Enables automatic Terraform planning.

when_modified

Specifies which changed files trigger autoplan.

*.tf

Terraform files in the project directory.

../modules/**/*.tf

Terraform files inside the modules directory and its subdirectories.

Why did we create this file?
Without this configuration, Atlantis may not know which directory contains your Terraform root module.

We used atlantis.yaml to tell Atlantis:

Where our Terraform configuration exists.

What to call our Terraform project.

Which files should trigger automatic planning.

Which Terraform workspace to use.

suppose i change a .tf file push the code to github how exactly we create a PR?
Bro, let's say you want to change the VM machine type from e2-medium to e2-small.

Here is the exact workflow.

Step 1: Make a change in your .tf file
For example, edit terraform.tfvars or the relevant Terraform configuration in your project.

Step 2: Create a new Git branch
In WSL, from your project root:

git checkout main
git pull origin main
git checkout -b change-vm-machine-type

A new branch keeps your changes separate from main.

Step 3: Commit and push your changes
git add .
git commit -m "Change VM machine type"
git push -u origin change-vm-machine-type

Now your new branch is available on GitHub.

Step 4: Create a Pull Request
Open your GitHub repository:

Open your repository

Click Pull requests.

Click New pull request.

Select:

Base: main

Compare: change-vm-machine-type

Add a title and description.

Click Create pull request.

GitHub Basics: 10 Steps Guide from Repo to Desktop - The Data School

Step 5: Atlantis automatically runs plan
Because your .tf file changed and matches the when_modified patterns in atlantis.yaml, Atlantis should automatically run Terraform plan.

You will see its plan result in the PR conversation.

Step 6: Apply the changes
After reviewing the plan, comment:

atlantis apply -p gcp-infrastructure

Atlantis applies the changes to GCP.

Remember this complete workflow
1. Modify Terraform .tf file

2. Git add, commit and push

3. Create GitHub Pull Request

4. Atlantis automatically runs PLAN

5. Review the plan

6. Comment atlantis apply

7. Merge PR into main
